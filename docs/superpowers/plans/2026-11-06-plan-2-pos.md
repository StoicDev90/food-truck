# Plan 2: POS (punto de venta) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** El empleado (o un dueño) abre turno, vende, cobra en ₲/R$/transferencia/tarjeta, anula, ingresa stock y cierra el turno a ciegas desde `/pos`, con la identidad visual Oasis Itaipu en tema noche y claro.

**Architecture:** La base de datos del Plan 1 ya hace todo lo transaccional (funciones `security definer`). Este plan agrega: la base visual compartida (tokens, fuentes, tema, logo), una capa server (`lib/pos/datos.ts` para leer, `lib/pos/acciones.ts` con Server Actions que llaman a las funciones de la base) y componentes cliente del POS. La lógica pura (formato, pedido, vuelto) vive en `lib/pos/*.ts` y se testea sin React.

**Tech Stack:** Next.js 16.4.5 (App Router, Server Actions, cacheComponents activo), React 19, Tailwind 4 + shadcn/ui (`base-nova`), Supabase, Vitest + React Testing Library.

**Spec:** `docs/specs/2026-11-06-food-truck-sistema-design.md` (comportamiento: §7, §9, §10) y `docs/specs/2026-11-06-identidad-visual-design.md` (aspecto: §5–§9, §11, §13). Si este plan y una spec chocan, manda la spec.

## Global Constraints

- Stack fijado: Next.js 16.4.5, Tailwind + shadcn/ui, Supabase, Vitest + RTL. `cacheComponents: true` queda activo: todo lo que lea `cookies()` va dentro de `<Suspense>`.
- **Toda página protegida y toda Server Action llama a `requerirAcceso('pos')` por su cuenta** (el layout solo no alcanza).
- **`productos` siempre con lista explícita de columnas**, nunca `select('*')` (el grant de columnas oculta `costo_gs`).
- Ventas, stock y caja se modifican solo vía las funciones de la base del Plan 1, llamadas desde Server Actions con el cliente de sesión (`crearClienteServidor`), nunca con service role.
- Errores de la base: códigos de `lib/errores.ts`; al usuario se le muestra `MENSAJES_ERROR[codigo]`; un error sin código → "No se pudo completar. Probá de nuevo."
- ₲ enteros, formato `₲ 31.000`; R$ con 2 decimales, formato `R$ 21,38`. Zona `America/Asuncion`.
- Colores solo por tokens (`bg-primary`, `text-marca`, …), nunca hex en componentes. Contraste ≥ 4.5:1 (identidad §7.2); nunca texto blanco sobre `#ec4899`.
- Fuentes: Fredoka (títulos, precios, montos, botones principales) y Nunito (resto), vía `next/font/google`.
- Objetivos táctiles ≥ 44 × 44 px; botones de producto ≥ 76 px de alto; botones de solo ícono con `aria-label` en español; íconos Lucide.
- Movimientos de caja: **solo dueños** (spec §10.5, cambio del 2026-11-06).
- Commits: paths explícitos; nunca `.claude/`, `.agents/`, `CLAUDE.md`, `skills-lock.json`, `docs/design/fotos/`, `.env.local`, `AGENTS.md`.
- Gate de cada tarea: `npm test && npm run test:db && npm run typecheck && npm run lint && npm run build`.

## Review Focus

1. **Doble clic / doble Enter en CONFIRMAR** → una sola venta: el botón se bloquea al primer evento y las dos llamadas comparten `clave`. → test en Task 7.
2. **Falla de red durante el cobro** → se muestra el error, el botón vuelve a habilitarse y el reintento usa **la misma** `clave` (no duplica). → test en Task 7.
3. **El stock cambió desde que se cargó la pantalla** (otra venta, otra pestaña) → `STOCK_INSUFICIENTE` con su mensaje, el pedido no se borra. → test en Task 7.
4. **El turno se cerró mientras el empleado vendía** (cierre forzado de un dueño) → `SIN_TURNO_ABIERTO` lleva a la pantalla de abrir turno, no deja la pantalla de venta colgada. → test en Task 7 (cobro) y Task 6 (refresh).
5. **Montos escritos a la manera local** ("50,5", "31.000", "R$ 50") → se interpretan bien; basura ("abc", "1,234") se rechaza antes de llamar al servidor. → test en Task 3.
